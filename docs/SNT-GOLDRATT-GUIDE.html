הסבר עצמאי ומפורט לרעיונות שבמאמר Strategy and Tactics מאת Eli Goldratt, Rami Goldratt ו־Eli Abramov, יחד עם האופן שבו ST Planner משתמש בהם לתכנון עמוק ולניהול ביצוע קליל.

הרעיון המרכזי

בכל רמה משמעותית יש זוג: Strategy = בשביל מה? Tactic = איך?

Strategy מתארת את התוצאה הנדרשת; Tactic מתארת את הדרך שנבחרה להשיג אותה. זו אינה חלוקה של “גבוה” מול “נמוך” — אותו יחס חוזר בכל רמה שבה עדיין יש החלטה מהותית.

Strategy

What for?
מה חייב להיות נכון כדי שהשלב יצליח?

Strategy טובה מנוסחת כתוצאה, לא ככלי או כפעילות.

Tactic

How?
איזו דרך נבחרה כדי לגרום ל־Strategy להתקיים?

ל־Tactic מהותית צריך להיות הסבר מדוע היא מתאימה למציאות ולמגבלות הנוכחיות.

Step אחד = Strategy + Tactic

Strategy
התוצאה שאנו חייבים להשיג
⇄
Tactic
הדרך שנבחרה להשיג אותה
ב־ST Planner לא מספיק לכתוב את הזוג. בהחלטה מהותית בודקים גם את ההנחות, חלופות סבירות שיכולות לשנות את הבחירה, ומה יפריך או יפתח מחדש את ההחלטה.

למה העץ היררכי?

Tactic של אב דורשת בדרך כלל כמה תוצאות עצמאיות. כל תוצאה כזאת הופכת ל־Strategy של ילד, ולה יש Tactic משלה.

Sx / Tx ├── S1 / T1 ├── S2 / T2 └── S3 / T3 S1 + S2 + S3 = necessary conditions all together = sufficient for Sx

הילדים צריכים להיות הכרחיים כל אחד בפני עצמו ו־מספיקים יחד.

העץ איננו ציר זמן

היררכיית S&T מסבירה למה ואיך — לא את סדר הביצוע.

prerequisites אמיתיים בין משימות implementation-ready נשמרים בנפרד ב־EXECUTION.md בעמודת Depends on.

Tactic אחת נבחרת לכל Strategy פעילה

מצבייצוג נכון
דרך אחת שנבחרה להשגת היעדStrategy אחת + Tactic אחת
כמה דרכים שכל אחת יכולה לבדה להשיג את אותו יעדחלופות; בוחרים את המתאימה ומצדיקים למה
כמה תוצאות שכולן נדרשותילדים נפרדים, לכל אחד Strategy/Tactic משלו

1. Tactic validity

הקשר: Tactic → Strategy של אותו Step.

שואלים למה ה־Tactic יכולה לעבוד כאן, אילו הנחות מחזיקות אותה, ואיזו חלופה מהותית עשויה להיות טובה יותר.

2. Necessity

הקשר: Child → Parent.

אם נמחק את הילד ולא נחליף אותו — האם האב עדיין יכול להצליח?

3. Sufficiency

הקשר: כל קבוצת הילדים → Parent.

נניח שכל הילדים הצליחו. איזו דרישה שהיינו אמורים לטפל בה עדיין יכולה להיות חסרה?

תנאי נחוץ שכבר מתקיים אינו משימה חדשה

אם תנאי נדרש כבר מתקיים במציאות הקיימת, אין צורך להפוך אותו ל־node או task רק כדי שהעץ ייראה שלם. מתעדים אותו כ־current reality או assumption רלוונטי וממשיכים.

זהו אחד ממנגנוני KISS החשובים: מתכננים את העבודה שצריך ליצור, לא את כל העובדות הנכונות בעולם.

איך עולים?

בשביל מה צריך את ה־Strategy הזאת?

התשובה עוזרת למצוא את התוצאה הגבוהה יותר שמצדיקה את השלב.

איך יורדים?

אילו תוצאות עצמאיות חייבות להתקיים כדי שה־Tactic הזאת תצליח?

התוצאות הנחוצות הופכות לילדים. ממשיכים עד שה־leaves decision-complete, מעשיים לביצוע ובר־אימות.

תהליך מעשי ב־ST Planner

1
הפרד outcome מפתרון מוצע.
הבן מה באמת צריך להיות נכון, מהי המציאות הנוכחית ומהן המגבלות.
2
בנה Strategy/Tactic והצדק את הבחירה.
בבחירה מהותית בדוק assumptions, alternatives ו־invalidation.
3
פרק לפי Necessity.
אל תפרק לפי תיקיות, צוותים או שלבי פיתוח אלא אם הם באמת תוצאות עצמאיות נדרשות.
4
בדוק Sufficiency.
נניח שכל הילדים הצליחו — האם האב עדיין יכול להיכשל בגלל פער שהיינו אמורים לתכנן?
5
עצור בזמן.
leaf מוכן כשלא נדרשת עוד החלטה מוצרית/ארכיטקטונית מהותית, הוא מעשי לביצוע ויש לו success evidence ברור.
6
בצע Final Planning Review.
בדוק מבחוץ פנימה outcome, alternatives, Necessity, Sufficiency, assumptions, evidence ו־KISS.
7
הפוך leaves ישירות למשימות.
ב־EXECUTION.md שומרים רק owner, status, prerequisites אמיתיים ו־result/evidence קצר.

דוגמה תוכנתית קצרה

הדוגמה נכתבה עבור המדריך ואינה מהמאמר המקורי.

0 Strategy: user can import CSV safely and predictably Tactic: bounded Parse → Validate → Persist → Report workflow ├─ 0.1 deterministic input interpretation ├─ 0.2 invalid data cannot reach persistence ├─ 0.3 accepted data persists with defined atomicity └─ 0.4 caller receives a deterministic outcome

כל ילד חייב לעבור Removal Test, וכל הקבוצה Gap Test. לאחר שה־leaves מוכנים לביצוע, הם יכולים להיות מוקצים ל־Chat N, agent או developer בלי ליצור task hierarchy שני.
